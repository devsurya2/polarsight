# Security audit report — POLARSIGHT platform

| | |
|---|---|
| Scope | Public website (`apps/web`, Next.js 16), admin portal (`apps/admin`, Vite + React), backend API (`apps/api`, Express + Prisma), PostgreSQL, file storage, local/compose infrastructure, CI |
| Standard | OWASP Top 10:2025, OWASP ASVS 5.0 **Level 2**, OWASP File Upload Cheat Sheet, OWASP Cheat Sheet Series |
| Method | Full source review of every route, middleware, query and configuration file; active probes against the local stack (`apps/api/tests/security.py`); dependency, secret and build verification |
| Date | 2026-11-11 |
| Environment | Local development stack only. No production system was touched |
| Outcome | 24 findings (6 high, 7 medium, 8 low, 3 informational). **All fixed and retested.** 7 residual risks documented |

This report describes what was found and what was done. It does not
claim the platform is "secure" in the absolute: it states which
classes of attack were tested, with what result, and what remains.

## 1. Architecture and attack surface

```
                 ┌──────────────────┐      ┌───────────────────┐
  visitors ────▶ │ Website :3000    │ ───▶ │                   │
                 │ Next.js (SSR)    │      │  API :5000        │      ┌────────────┐
                 └──────────────────┘      │  Express          │ ───▶ │ PostgreSQL │
                                           │  cookie sessions  │      └────────────┘
  admins ──────▶ ┌──────────────────┐ ───▶ │  RBAC + re-auth   │ ───▶ clamd :3310 (loopback)
                 │ Admin :3001      │      │  CSRF guard       │ ───▶ SMTP (optional)
                 │ Vite SPA, proxied│      │  rate limits      │ ───▶ website /api/revalidate
                 └──────────────────┘      └───────────────────┘
                                                   │
                                      ┌────────────┴─────────────┐
                                      │ uploads/ (public, scanned)│
                                      │ private-uploads/ (never   │
                                      │   served: resumes,        │
                                      │   quarantine)             │
                                      └──────────────────────────┘
```

Trust boundaries: internet → website/forms; internet → admin portal
(authenticated); API → database; API → scanner; API → mail. The API is
the single enforcement point: both front ends talk only to it, and
neither front end holds a secret. The full endpoint inventory is in
API_SECURITY_DOCUMENTATION.md; the personal-data flow for enquiries,
applications and resumes is described there too.

No webhooks, no third-party scripts, no server actions, no raw SQL
beyond `SELECT 1`, no `dangerouslySetInnerHTML`, no `eval`, no child
processes. Secrets live in the repository-root `.env` (git-ignored;
history scanned clean with gitleaks) and are validated at boot.

## 2. Findings by OWASP category

**A01 Broken access control** — PS-02 (account takeover of a more
privileged administrator through account-management routes), PS-03
(revoked permissions honoured until token expiry), PS-01 (private
files reachable through the public media path). RBAC itself — every
route enforcing a permission server-side, delegation limited to what
the caller holds, last-Super-Admin protection, curriculum ownership
re-checked, drafts unreachable from public endpoints — was sound and
is covered by 220 integration checks.

**A02 Security misconfiguration** — PS-06 (proxy headers trusted
unconditionally), PS-08 (CORS refusal as a 500; no explicit CSRF
check), PS-12 (no security headers on either front end), PS-20
(public cache header on form POSTs), PS-21 (admin source maps shipped).

**A03 Software supply chain** — PS-17 (`nodemailer` advisories, high),
PS-18 (`multer` 1.x), PS-23 (no scanning in CI, no SBOM). After fixes:
`npm audit` reports 0 advisories at every level; a CycloneDX SBOM
(535 components) is generated by `npm run security:sbom`; CI blocks on
moderate+ advisories, leaked secrets, Semgrep findings and undocumented
destructive migrations.

**A04 Cryptographic failures** — No findings. Passwords: bcrypt cost 12.
Refresh tokens: 48 random bytes, stored as SHA-256 digests. Preview
links: HMAC-SHA256, constant-time compare, 10-minute expiry. Added:
TOTP seeds encrypted at rest (AES-256-GCM, `MFA_ENCRYPTION_KEY`),
recovery codes stored as digests. Production boot refuses equal JWT
secrets, insecure cookies, a missing scanner or a missing MFA key.

**A05 Injection** — No exploitable finding. Prisma parameterises every
query; search inputs are text. Every editable string refuses markup,
scripts, `javascript:` and template syntax; page documents are screened
recursively. Both front ends render content as text. Added: PS-13
(line breaks in names headed for email headers). SVG screening now
decodes numeric entities first.

**A06 Insecure design** — The threat model (section 4) drove PS-11
(quarantine + scanning), PS-15 (MFA), PS-16 (re-authentication) and
PS-19 (per-address sign-in throttle).

**A07 Authentication failures** — PS-04 (sign-out did not kill the
access token), PS-05 (token in the response body), PS-14 (lockout
message), PS-15, PS-16, PS-19. Retained strengths: lockout after 8
failures, refresh rotation with family revocation on reuse, immediate
revocation via `sessions_valid_from`, one failure message, ≥12-char
passwords with class requirements.

**A08 Software or data integrity** — PS-10 and PS-11 (file integrity
and scanning), PS-09 (parser failures). Content publishing re-validates
at publish time and snapshots every publish; the website's revalidate
route requires a shared secret compared in constant time.

**A09 Logging and alerting** — Already strong: an append-only audit
table with no write endpoint, scrubbed before/after snapshots, failed
sign-ins recorded against the typed address, resume downloads and
exports audited, pino redaction of cookies/authorization/passwords.
Added events: `auth.mfa_*`, `auth.reauth*`, `upload.malware_rejected`,
`application.resume_rescanned/rejected`, `media.rescanned/rejected`.

**A10 Mishandling of exceptional conditions** — PS-09; scanner errors
fail closed (a file is never approved because the scanner was
unavailable); status changes and their history are single transactions;
upload parsing is bounded (size, field counts) before any processing.

## 3. Severity scale

| Severity | Meaning |
|---|---|
| Critical | Unauthenticated remote compromise or mass data exposure |
| High | Exploitable by an anonymous or low-privilege actor to access or alter data they must not, or a mandated control absent |
| Medium | Exploitable with preconditions, or materially weakens another control |
| Low | Hardening, information leakage, defence-in-depth gap |
| Informational | Process or hygiene |

## 4. Threat model (summary)

| Actor | Goal | Controls now in place |
|---|---|---|
| Malicious applicant | Deliver malware to a reviewer; exhaust storage | PDF-only policy with structural/active-content inspection; quarantine + clamd; downloads only when CLEAN; 5 MB cap; 5/h per address; duplicate suppression |
| Bot | Spam forms; enumerate accounts | Honeypots; per-address limits; one sign-in failure message; CSRF/Origin checks |
| Unauthorised user | Reach admin data | Every admin route behind session + permission; drafts/notes/IPs never selected publicly; private files never served |
| Compromised administrator account | Escalate; exfiltrate | Delegation and hierarchy rules; MFA; re-auth before sensitive actions; immediate session revocation; exports audited and note-free |
| Insider | Tamper with the trail | Append-only audit table; DML-only DB role (`docs/security/sql/least-privilege.sql`) |
| Database compromise | Replay sessions; read seeds | Only token digests stored; TOTP seeds encrypted; passwords bcrypt |
| Storage compromise | Serve or run uploads | Random keys, `0600` files, sandboxed static responses, private tier outside the web root |

## 6. What remains

See the residual-risk table in VULNERABILITY_REGISTER.md and the
recommendations in SECURITY_CONFIGURATION_GUIDE.md. The most important:
production must run behind TLS with `TRUST_PROXY=true`, a reachable
clamd, a dedicated `MFA_ENCRYPTION_KEY`, the DML-only database role,
and the website CSP should move to nonces when a middleware is added.
